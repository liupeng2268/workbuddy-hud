# 按文件明细记账

**状态**: 已采纳

## 背景

[0001](0001-双口径记账权归属.md) 把两套口径的记账权分开后，仍留下一处已知限制：文件被截断或重写时，读取位置回到开头，而全局计数器只会累加。于是同一份被读过的数据又被记一遍，且没有任何回退手段。

只要计数是「无状态的全局求和」，就无法回答一个本来很自然的问题：某个文件究竟贡献了多少。切换会话时会话口径靠清零重来，历史口径却永不重置，误差只能一直留着。

## 决策

把「某个文件贡献了多少」记成该文件的明细，随它的读取位置一起保存。全局计数器不再直接接收解析结果，而是接收「这批新解析出来的增量」；文件被截断或重写时，先把它此前贡献的明细扣回，再从头重算。

明细是计数类的：命中、未命中、提示、已缓存、输出、记录数。速率样本与会话的时间范围不做按文件回滚，它们只影响短时曲线，截断后短暂失真可以接受。

读取状态因此包含三样东西：读到哪里、是不是行首、以及这份文件已经贡献了多少。

## 考虑过的方案

- **按记录去重**：维护已入账记录的指纹集合，重复即跳过。能顺带覆盖「文件被原地改写但大小不变」的情况，但内存随历史规模线性增长，查找与维护成本都高。不采纳。
- **截断时把全局计数整个清零重扫**：实现最省事，但会把所有无关文件的历史一并作废，界面出现长时间空窗。不采纳。
- **检测文件身份（inode / 修改时间）后整体重置**：能覆盖更多改写场景，但跨平台行为不一致，且每个文件每轮都要多一次系统调用。列为后续可选项，本次不引入。

## 后果

- 截断与重写不再让计数翻倍，会话与历史两套口径都适用。
- 运行期新出现的大文件，历史口径可以从头读完整，而不必只回溯末尾一段；头部数据不再永久丢失。代价是这类文件要分几轮读完，首次全量期间会占用既有的字节预算。
- 「文件被原地改写但大小未变小」仍无法识别，仍会重复计数。这是明确的剩余边界：判别它需要文件身份信息，留待后续评估。
- 会话口径的时间范围、模型名与速率样本在截断后不回滚，短时曲线可能短暂失真。这是为了不把明细机制扩大到非计数类状态而接受的代价。
